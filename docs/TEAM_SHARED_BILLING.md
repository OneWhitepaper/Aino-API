# 团队共享额度

用户侧入口为“额度使用方式”(`/funding`) 和“团队共享管理”(`/team-sharing`)。

## 资金与权限

- 组织人的余额为同一个资金池，不复制、不预分配给成员。个人余额和个人订阅独立保留。
- 邀请面向已存在的用户 ID，需要目标用户接受，有效期 7 天；系统不发送邮件。
- 成员上限是加入该团队以来的累计共享消费上限，覆盖共享余额和共享订阅。`null` 表示不限，`"0"` 表示不允许继续共享；重新加入不会清零历史消费。
- 暂停、移除和退出撤销后续共享授权。已派发的请求按原快照结算，历史记录保留。
- 组织人选择共享哪些订阅、余额和订阅的顺序，并可设置成员覆盖。组织人的个人来源建议不会覆盖成员的个人付款授权。
- 共享订阅只授予被选中且有效订阅的对应分组权限，仍受模型、有效期和日／周／月限制约束。
- 单次请求只选择一个付款来源，不拆分账单、不递归使用另一个团队。模型价格与倍率继续使用调用人的分组设置。

## 成员付款方式

个人来源仍受成员授权开关控制；未授权的来源从下列顺序中移除。

| 方式 | 顺序 |
| --- | --- |
| 优先个人余额 | 个人余额 → 个人订阅 → 所选团队 |
| 仅用个人余额 | 个人余额 |
| 优先团队共享额度 | 所选团队 → 个人订阅 → 个人余额 |
| 仅用团队共享额度 | 所选团队 |
| 优先个人订阅 | 个人订阅 → 个人余额 → 所选团队 |
| 仅用个人订阅 | 个人订阅 |

团队内部使用其有效的默认／成员级共享资源顺序。“仅用”耗尽时不会改扣另一类来源。新来源只能在派发前选择，派发后不切换付款人。

未设置偏好的普通用户保持既有扣费行为。创建团队的组织人自动进入资金池并发保护；未保存偏好时仍按原分组的余额或订阅方式付款。

## 当前请求支持范围

共享付款支持 `/v1/chat/completions`、`/v1/responses`、`/v1/messages` 的独立文本请求，包括流式输出和本地函数工具定义／结果。文本请求未提供输出上限时补充 4096；显式上限保留，预留按保守费用上界计算。

图片、音视频、异步任务、WebSocket、服务端会话引用、托管收费工具、远程附件和无法确定计费模型的路由暂不使用共享付款，返回 `TEAM_FUNDING_COST_UNBOUNDED`。如果上游转换移除了输出上限，共享请求也会在网络派发前拒绝。现有个人媒体请求保留原处理方式。

桌面端继续使用原账号、设备凭据、模型目录和 `billing_source: balance|subscription` 协议，后台保存调用人与付款人。个人钱包接口不合并团队资产。

## 账务与恢复

- PostgreSQL 预留占用真实余额或订阅窗口，成员上限检查与预留在同一事务中完成。
- 付款快照和预留随请求保存；结算加入已有用量去重事务，同时更新付款人、成员消费和团队账本。
- 客户端应对一次逻辑操作复用 `Idempotency-Key`，桌面端也可使用既有操作／调用标识。未提供重试标识的两次独立 HTTP 请求不能识别为同一操作。
- 单次操作由数据库保证只有一次上游派发；不会在未知结果后自动重试另一账号或付款来源。
- 未派发请求释放预留；明确且无用量的上游拒绝可释放。网络中断、未知响应或已派发但未结算的请求不按超时自动退款，需运维依据上游用量核对。
- 正常结算退回多余预留。若实际费用意外高于已授权上界，超出部分单独保存供核对，不擅自多扣个人资金或突破成员上限；相关共享资源暂停后续使用。
- 团队账本的 `amount` 为实际扣费，`unauthorized_amount` 为未计入实际扣费的待核对金额。旧请求跨越共享启用时的未支付差额保存在 `funding_billing_shortfalls`。

数据库迁移为 `257_team_shared_billing.sql`、`258_personal_funding_reservations.sql`、`259_funding_billing_shortfalls.sql`。上线前应备份数据库，并保留预留、账本和去重记录以供核对。
